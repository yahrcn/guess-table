# Угадай персонажа

Браузерная онлайн-версия игры «Угадай кто» на двоих: поле 5×5 карточек, приватный выбор секретной карточки, вопросы да/нет по очереди, личное вычёркивание неподходящих карточек и финальная догадка. Доступ в комнату — по прямой ссылке, без матчмейкинга.

## Стек

- **Клиент:** React + Redux Toolkit (слайсы + redux-saga) + CSS Modules + Vite + Socket.IO client
- **Сервер:** Node.js + Express + Socket.IO
- **Монорепо:** npm workspaces (`packages/shared`, `packages/server`, `packages/client`)

## Наборы карточек

Семь наборов по **50** карточек каждый — выбирает создатель комнаты в лобби, пока ждёт второго игрока (см. [`cards.ts`](packages/shared/src/cards.ts)). На само поле 5×5 каждая партия тянет случайные 25 из этих 50 (`BOARD_SIZE`, см. `Room.ts`), так что одна и та же колода не повторяется от игры к игре один в один:

- Вымышленные персонажи
- Известные личности (только давно умершие исторические фигуры — никаких вопросов о праве на изображение живых людей)
- Животные
- Профессии
- Фильмы
- Видеоигры
- Актёры и актрисы (ныне живущие, самые популярные — в отличие от «Известных личностей» выше это осознанное исключение: раз набор про тех, кто популярен *сейчас*, исторических фигур тут быть не может; как и везде — только имя как текст, никакого реального фото)

Для «Известных личностей», «Актёров и актрис», «Фильмов» и «Видеоигр» используются только текстовые названия/имена — ни одной реальной фотографии, обложки, кадра или логотипа в приложении нет и не подгружается.

Иллюстрация на карточке — SVG, но **не вычисляется из хэша строки**: у каждой из 350 карточек своя, вручную подобранная запись в таблице дизайна (`*Designs.ts` рядом с каждым генератором), которую рисует один из трёх рендереров:

- [`Avatar`](packages/client/src/components/Room/components/Avatar/Avatar.tsx) + [`personDesigns.ts`](packages/client/src/components/Room/components/Avatar/personDesigns.ts) — лица (вымышленные персонажи, известные личности, профессии, актёры). У профессий и части известных личностей есть предметный значок в углу (`badges.tsx`): стетоскоп у врача, колба у учёного, перо у писателя и т.д. — это и есть «индивидуальность» карточки, а не продукт формулы. У актёров/актрис свой значок — пятиконечная звезда («шоу-бизнес»), плюс причёска/цвет волос/очки подобраны так, чтобы все 50 лиц визуально отличались друг от друга, а не сливались в одно и то же обобщённое лицо.
- [`AnimalAvatar`](packages/client/src/components/Room/components/AnimalAvatar/AnimalAvatar.tsx) + [`animalDesigns.ts`](packages/client/src/components/Room/components/AnimalAvatar/animalDesigns.ts) — морды животных с осознанно подобранной характерной деталью под конкретный вид: грива льву, рог носорогу, хобот слону, длинная шея жирафу/лебедю/журавлю, панцирь черепахе, клюв птицам.
- [`MediaAvatar`](packages/client/src/components/Room/components/MediaAvatar/MediaAvatar.tsx) + [`mediaDesigns.ts`](packages/client/src/components/Room/components/MediaAvatar/mediaDesigns.ts) — «плитка» для фильмов/видеоигр с иконкой-пиктограммой, выбранной по смыслу названия (меч для RPG, корабль для «Титаника», блоки для «Тетриса» и т.п.).

Выбор рендерера под набор — в [`DeckAvatar.tsx`](packages/client/src/components/Room/components/DeckAvatar/DeckAvatar.tsx). Это честный средний путь между «всё по хэшу» (как было раньше) и «300 независимых произведений цифрового искусства» (нереалистично по объёму для одной сессии): никакого хэширования нигде нет, каждая карточка имеет явно прописанное мной сочетание атрибутов/иконки, но сами атрибуты рисуются переиспользуемыми примитивами внутри рендерера набора, а не являются полностью независимой векторной разметкой с нуля.

Добавить новый набор: значение в `DeckId`, 50 карточек в `CARD_DECKS` и подпись в `DECK_LABELS` (`packages/shared/src/cards.ts`), плюс запись в соответствующей `*Designs.ts` (или новый генератор + таблица, если набор не похож на существующие) и ветка в `DeckAvatar`.

### Свои изображения вместо сгенерированных

Положите файл `<id карточки>.jpg` (или `.jpeg`/`.png`/`.webp`) в [`packages/client/public/cards/`](packages/client/public/cards/README.md) — карточка покажет его вместо сгенерированной иллюстрации, никакого кода менять не нужно ([`CardImage.tsx`](packages/client/src/components/Room/components/CardImage/CardImage.tsx) сам пробует файл и откатывается на генератор, если файла нет). Мы сами не скачиваем и не храним никаких изображений — ответственность за права на то, что вы сюда положите, на вас.

## Структура

```
packages/
  shared/   # общие типы, контракт socket-событий, колода карточек, нормализация вопросов
  server/   # Express + Socket.IO, игровая стейт-машина комнаты (RoomManager/Room)
  client/   # Vite + React + Redux Toolkit
    src/
      entries/App        # корневой компонент SPA
      config/             # store, корневой редьюсер/сага, типизированные хуки
      pages/              # тонкие роуты (HomePage, RoomPage) — без логики
      components/
        Home/             # фича «создать комнату»: slice + selectors + sagas + UI
        Room/             # фича «игра в комнате»: slice + selectors + sagas + UI + components/*
      shared/
        components/       # переиспользуемые UI-куски (Button)
        session/          # личность игрока (playerId/token/roomId) — сквозной слайс
        helpers/          # localStorage-хелперы
        socket/           # Socket.IO клиент и типизированные запросы
```

Код фронтенда следует конвенциям из `billy-frontend-code-style`: слайсы redux-toolkit с фабриками `create[Имя]State`, экшены вида `fetch/select/ask/answer/finalGuess[Begin|Success|Error]` с объектным payload'ом, вся сетевая логика — в сагах (а не в `useState`/прямых вызовах из компонентов), строковые enum'ы (`Phase`, `FinishReason`, `AsyncStatus`, `ConnectionStatus`), `cx`/`classnames` для условных классов, страницы — тонкие обёртки над «фичами» в `components/`. Инфраструктурно-специфичные для Контура правила (react-ui, `@skbkontur/icons`, `@skbkontur/colors`, сгенерированные api-клиенты, `Url.Action`, `ErrorBoundary`-HOC) не применялись — этих пакетов в проекте нет, а `connect()`/`Container`-обёртка не нужна, так как подключение к стору всюду через хуки (`useAppSelector`/`useAppDispatch`), без динамической инжекции редьюсеров.

## Запуск локально

```bash
npm install
npm run dev
```

Поднимутся:
- сборка `shared` в режиме watch,
- сервер на `http://localhost:4000`,
- клиент (Vite) на `http://localhost:5173` (dev-сервер проксирует `/socket.io` на сервер).

Откройте `http://localhost:5173` в двух разных вкладках (одна — в режиме инкогнито, чтобы не делить localStorage), в одной нажмите «Создать игру», скопируйте ссылку на комнату и откройте во второй.

## Сборка и запуск в продакшен-режиме

```bash
npm run build   # соберёт shared -> client -> server
npm start       # запустит собранный сервер; он же отдаёт клиентскую статику
```

В продакшене один Node-процесс слушает один порт: отдаёт и собранный клиент (`packages/client/dist`), и WebSocket (Socket.IO) — поэтому не нужен отдельный хостинг под фронтенд и не нужно настраивать CORS.

## Аналитика и админка

Сервер опционально логирует партии в Postgres: кто и когда создавал игру, какой набор карточек выбрали, какие вопросы задавали (с текстом и нормализованной формой — для подсчёта самых частых), сколько длилась партия и кто победил. Игрок идентифицируется стабильным анонимным `clientId`, который генерируется в браузере и живёт в `localStorage` — никакой регистрации или личных данных нет.

- **Переменные окружения** (см. [`packages/server/.env.example`](packages/server/.env.example)):
  - `DATABASE_URL` — строка подключения к Postgres. Не задана — логирование и `/admin` тихо отключаются, сама игра работает как обычно (ни одного запроса к БД не выполняется).
  - Вместо `DATABASE_URL` можно задать отдельные `POSTGRESQL_HOST`/`POSTGRESQL_PORT`/`POSTGRESQL_USER`/`POSTGRESQL_PASSWORD`/`POSTGRESQL_DBNAME` — именно в таком виде Timeweb Cloud Databases отдаёт реквизиты managed Postgres. Используются только если `DATABASE_URL` не задан.
  - `DATABASE_SSL=true` — включить для managed Postgres (Timeweb Cloud Databases и т.п.), которым обычно нужен SSL. Для локального `docker-compose` не указывать.
  - `ADMIN_PASSWORD` — пароль для Basic Auth на `/admin` и `/api/admin/stats`. Не задан — обе ручки отвечают `503`.
- **Схема БД** создаётся/обновляется сама при старте сервера (`runMigrations()`, идемпотентные `CREATE TABLE IF NOT EXISTS` — см. [`db/migrate.ts`](packages/server/src/db/migrate.ts)), никакого отдельного шага миграции руками не требуется.
- **Локальный Postgres для разработки:**
  ```bash
  docker-compose up -d
  ```
  поднимет Postgres на `localhost:5432` с базой `guesstable` (см. [`docker-compose.yml`](docker-compose.yml)). Скопируйте `packages/server/.env.example` в `packages/server/.env` и запустите `npm run dev` как обычно.
- **`/admin`** — страница со статистикой (самые активные игроки, частые вопросы, популярность наборов карточек, длительность партий) за Basic Auth; графики — простые bar-чарты на чистом HTML/CSS/JS, без внешних библиотек и CDN.

## Favicon и SEO

- **Favicon** — [`favicon.svg`](packages/client/public/favicon.svg): векторный знак вопроса на фирменном оранжевом фоне, нарисован вручную (дуга + линия + точка), без внешних иконок/эмодзи. PNG-версии (`favicon-32x32.png`, `apple-touch-icon.png` 180×180, `icon-512.png`) сгенерированы из того же дизайна растровым рендерером, который временно жил в `scratch-favicon.js`/`scratch-og.js` в корне репозитория (сами скрипты удалены после использования — если понадобится перегенерировать иконки другого размера или с другим рисунком, писать подобный скрипт заново).
- **`og-image.png`** (1200×630) — превью для ссылок на комнату в мессенджерах (Telegram/WhatsApp/VK и т.п.): несколько карточек в фирменных цветах игры со значком вопроса, без текста (заголовок/описание показывает сама площадка из `og:title`/`og:description`).
- **Теги в `<head>`** ([`index.html`](packages/client/index.html)): `title`/`description`, Open Graph и Twitter Card, `theme-color` (светлая/тёмная тема), `manifest.webmanifest`. Поскольку домен на этапе сборки неизвестен, `og:image`/`og:url`/`canonical` прописаны в HTML как относительные пути, а на реальный абсолютный адрес их достраивает [`absolutizeSeoTags()`](packages/client/src/shared/helpers/seoHelpers.ts) при старте приложения — благодаря этому превью ссылки на конкретную комнату (`/room/:id`) показывает URL именно этой комнаты, а не всегда главную страницу.
- **`robots.txt`** разрешает индексацию главной страницы, но запрещает `/room/*` — комнаты создаются по прямой ссылке без матчмейкинга, и незачем им светиться в поиске. Ссылается на `sitemap.xml` (единственная значимая для индексации страница — главная, домен `guesswho.su` зашит в оба файла; при смене домена поправить оба).
- **Яндекс.Вебмастер**: подтверждение владения через HTML-файл — `packages/client/public/yandex_<код>.html` (копия файла, выданного Вебмастером), раздаётся как есть по корню сайта.

## Чеклист деплоя (Timeweb Cloud)

Используем [Timeweb Cloud Apps](https://timeweb.cloud/docs/apps) — он запускает произвольный Node.js-процесс и умеет WebSocket (в отличие от обычного shared-хостинга). Разворачиваем **одно** приложение: в проде Express-сервер сам раздаёт собранную React-статику и держит Socket.IO на одном порту — отдельного «React-приложения» заводить не нужно.

1. Запушить репозиторий на GitHub (или GitLab).
2. В Timeweb Cloud создать новое приложение, подключить репозиторий.
3. На шаге выбора типа/фреймворка выбрать **Express** (Node.js), не React — React в проде обслуживается тем же Express-процессом через `npm run build`.
4. **Корневая директория (root):** оставить пустой (не указывать) — она нужна только для монорепо с проектом в подпапке, а нам, наоборот, нужна сборка из корня, где лежит `package.json` с workspaces.
5. **Команда установки/build command:** `npm install --include=dev && npm run build` — именно `--include=dev`, а не просто `npm install`. Переменная `NODE_ENV=production` (см. ниже) иначе заставит npm пропустить все `devDependencies` (`typescript`, `vite`, `tsx`) прямо на шаге установки, и сборка упадёт с `tsc: not found`.
6. **Start command:** `npm start`
7. **Версия Node.js:** любая современная LTS (20/22/24).
8. **Переменные окружения:** `NODE_ENV=production` (порт платформа обычно пробрасывает через `PORT` — сервер уже читает `process.env.PORT`). Если нужна аналитика и `/admin` — добавить `DATABASE_URL` (из созданной на шаге 9 базы), `DATABASE_SSL=true`, `ADMIN_PASSWORD`. Без них игра работает как обычно, просто без логирования.
9. (опционально, для аналитики) В Timeweb Cloud создать managed Postgres (Timeweb Cloud Databases), взять оттуда строку подключения для `DATABASE_URL` — схема создастся сама при первом старте сервера.
10. Убедиться, что в настройках приложения включена поддержка WebSocket/долгоживущих соединений (должно быть по умолчанию для Cloud Apps).
11. HTTPS включается платформой автоматически — Socket.IO сам переключится на `wss://`.
12. Открыть выданный URL в двух вкладках/окнах (одно — инкогнито), создать игру в одном, скопировать ссылку на комнату, открыть во втором — пройти полный цикл партии.
13. (опционально) подключить свой домен, настроить мониторинг логов платформы.

> Точные названия полей в мастере создания приложения могут отличаться от описанных выше — ориентируйтесь по смыслу (тип/фреймворк, корневая директория, build/start-команды, переменные окружения). Любой другой PaaS с поддержкой произвольного Node.js-процесса и WebSocket (Render, Fly.io, Railway, Amvera) разворачивается по той же логике.

## Правила, зашитые в сервер

- Каждая комната рассчитана ровно на двух игроков; третий получит ошибку «комната заполнена».
- Секретная карточка каждого игрока хранится только на сервере и никогда не попадает в снимок состояния оппонента.
- Повторный одинаковый вопрос в рамках одной партии отклоняется сервером (сравнение после `trim` + нижний регистр + схлопывание пробелов/пунктуации — см. [`normalizeQuestion`](packages/shared/src/normalizeQuestion.ts)).
- Неверная финальная догадка не завершает партию: угаданная карточка навсегда блокируется у игрока (её нельзя ни кликнуть повторно, ни снять с исключения вручную — в отличие от обычных личных пометок), а ход переходит сопернику. Побеждает только тот, кто назвал карточку верно.
- При разрыве соединения игрок не исключается из партии: переподключение по сохранённому в `localStorage` токену восстанавливает его место в той же комнате (на клиенте это отдельная сага, слушающая переподключение сокета — см. [`components/Room/sagas.ts`](packages/client/src/components/Room/sagas.ts)).
- Неактивные комнаты (без действий более 2 часов) удаляются из памяти сервера.
- «Сыграть ещё» (`game:rematchBegin`) сбрасывает партию в той же комнате — новая перетасовка поля, секреты и лог вопросов очищаются — но только после того, как оба игрока подтвердят готовность (набор карточек при реванше остаётся тот же, что был выбран изначально).
- Набор карточек (`game:selectDeck`) может сменить только первый игрок в комнате (создатель) и только пока она в статусе «лобби» — после входа второго игрока фаза лобби сама заканчивается и выбор блокируется.
- Получатель вопроса может подать аппеляцию (`game:appealQuestion`) вместо ответа Да/Нет — с причиной «такой вопрос уже был» или «вопрос некорректен». Вопрос считается не заданным (его нельзя больше ни отменить, ни ответить на него), а ход остаётся у того, кто спрашивал — аппеляция просто обнуляет попытку, а не отдаёт её сопернику. Сервер сам оценивает обоснованность: «уже был» проверяется пересечением слов с предыдущими вопросами партии, «некорректен» — по словам-маркерам открытого вопроса («как», «что», «кто» и т.п. без «ли»). Игрок, у которого минимум 3 аппеляции и доля обоснованных ниже 50%, теряет доступ к кнопке до конца партии (видно только ему самому). Все аппеляции попадают в общий лог партии и (если настроена БД) в таблицу `appeals` для статистики в `/admin`.

## Известные ограничения MVP

- Состояние живёт в памяти процесса — при перезапуске сервера все активные партии теряются (достаточно для single-instance деплоя из чеклиста выше; для горизонтального масштабирования понадобится вынести состояние в Redis).
- Нет автотестов — логика проверялась вручную по сценарию из раздела «Запуск локально».
- «Сыграть ещё» требует согласия обоих игроков (оба должны нажать кнопку после завершения партии) — если один из них закрыл вкладку насовсем, реванш в этой комнате так и останется в ожидании.
